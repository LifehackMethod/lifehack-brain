# Phase 3 — propose, ask once, prove the handoff (steps 3.5 → 4)

Everything here **drafts**. One step asks. Then a blind reader proves the result, and the harvest lands.

---

## Step 3.5 — Draft the plan amendments

A gated write to the **linked plan only**.

**Draft an edit only if BOTH hold** — otherwise you still owe the receipt at 3.57, because a bare
*"plan current"* with no stated reason is the failure this exists to fix:

1. **A meaningful change** — the reconciliation found real deltas: steps now done, obsolete, or
   overtaken, or a new dead end. Cosmetic drift does not qualify.
2. **High confidence.** If you are unsure whether a step is truly stale, **do not edit it** — surface it
   as a question, **with a drafted edit attached.**

**Hard guardrail: never edit the plan's frame or definition of done.** That changes only on explicit
direction in the session.

**Any amendment carries a task's full shape:** which lanes it can run in parallel with (or what gates
it), a gear tag, **a named model on every delegated task** — blank inherits the session's most expensive
tier — and a **runnable verify** (a command or a rendered check, never "looks done").

**Scope reconciliation, in the same pass.** Does every success criterion still map to a task? Anything
that does not either **gains a task** or **moves to `⚠ CUT`** — never let it vanish silently.

⭐ **And the return loop, which runs here because this skill runs far more often than a planner does.**
Walk backwards: derive from the rungs and current state what the plan *should* hold now, diff that
against what it *does* hold, and put every open task in one bucket — **still serves** · **done another
way** (✅ + what did it) · **superseded** (✗ + what replaced it) · **❓ can't tell** (→ them, and this
one is never rounded away). ⛔ **Additive only — a marker beside the task, never a removal.** Finished
work stays; that protects the record from destruction, and it was never a rule against re-reading.
**Measured:** one plan carried 75 open tasks, 58 of them from earlier sessions that nothing had
revisited.

**Draft here; do not ask here.** Everything goes into the single round at 3.57.

**Always draft the concrete edit — never a bare "the plan looks stale."** The failure mode is reporting
staleness and stopping, leaving the person to do the update themselves. The moment you spot a stale
step, produce the actual change: mark it done, rewrite it with the new reality, append the dead end.

## Step 3.55 — Draft the brief deltas, and the rungs

**Scope: exactly two sections** — the `## 2. CURRENT STATE` narrative and the success criteria. **Not**
the frame (observe-and-flag only). **Not** the story log (append-only, handled at 3.6). **Not** heavy
re-tiering — that is `/save`.

**Plus the three-rung block, and there is one rule for it:** *"I see the three-tier altitude printed
cleanly. And then everything below that is a list of proposals of things it would change. And then I
approve, and then it gets written."* **Missing · badly worded · drifted · sitting on competing
surfaces — all four go to the panel as item 0**, and are written only on a yes. See `SKILL.md` for why
the write-directly licence is deleted and must not be restored.

**What phase 1's five checks feed in.** They are **reported separately** — they are different failures
needing different fixes — but they converge on **one** panel item:

- **Draft the concrete replacement, never a bare verdict.** *"The 5,000 looks stale"* is not a proposal.
  Write the rung you would put there, in full.
- **A rung that is both drifted and badly worded gets ONE replacement that fixes both** — never a
  grammar pass now and a reword later.
- **If check 4 found competing surfaces, removing them is part of the same item-0 proposal.** Writing a
  correct block without removing its rivals is a net loss.
- **On a no, leave it untouched.** The drift still shows in the orientation block and the receipt, and
  step 0.8 already showed them the current text — nothing is hidden by declining.

**Composing a rung:**

- ⛔ **Read, don't compose from memory.** The 5,000 is quoted from the live plan or the seam this
  session is inside. A rung written from memory is not a rung — and neither is one copied forward from
  the block's own prior text without re-checking it against this session. **That is exactly how the
  instrument-versus-patient drift happened.**
- ⛔ **A rung with no honest answer says so** — *"no larger frame"*, *"no plan armed"*. Never invent one
  to fill the space. **A fabricated rung reads exactly like a real one**, and that is what trains a
  reader to skim the whole block.
- ⛔ **Position, not restated intent.** The 10,000 states how far the project has come **against** the
  desired outcome. A line that re-quotes the frame is wrong: it duplicates it, rots independently of
  it, and produces a block readers skim.
- ⛔ **Write for a blind reader** — every proper noun gets a clause, every sentence a subject and a
  verb, every ambiguous word disambiguated in place.
- ⭐ **The ceiling, stated plainly.** This makes the block far more likely to exist, stay current and
  stay legible. **It is not enforcement and cannot be.** This is prose; it has no mechanical way to
  guarantee the block is right. A real gate would be a schema checker, and none exists.

### Verb B — the graduation. CLOSE mode only, and not optional.

Everything above fixes what the section **says**. **Nothing fixes how BIG it is.** A live run made three
accurate corrections and still ended `OVERSIZED` at 151.9% — the content became true and the section
stayed huge. That session correctly said *"that's a compaction pass, belongs to /save"* — **and `/save`
had no reference to that section at all.** The loop dead-ended and the brief stayed oversized forever.

**In PICKUP mode this does not run.** Stamp `graduate --ns checkin --verdict NOT_OWED`.

> ⛔ **Why a pickup window must never graduate.** Deciding whether a paragraph is a **settled decision**,
> a **dead end**, or a **still-open thread** requires knowing what happened — and it moves content into
> an **append-only** log where a wrong call cannot be taken back. A blind window would be guessing at
> the meaning of yesterday's content. **The session that did the work is the only one that can graduate
> it.**

> ⛔ **And in CLOSE mode it is unconditional — no verdict gate.** An earlier draft fired it only on an
> `OVERSIZED` verdict. **That is how the section reached 799 lines in the first place:** it only got
> cleaned once it was already too big. **The scratchpad does not wait until it is bloated, and neither
> does this.** `OVERSIZED` is a symptom of this step never having run — never its trigger.

**UPDATE → AUDIT → COMPACT, in that order.** The order is load-bearing: compacting first graduates
**stale** content into an append-only log you cannot then correct.

1. **UPDATE** — the content deltas above. Already done by now.
2. **AUDIT** — the board against itself and against the story log: a ✅ LOCKED item a ⛔ RULED-OUT line
   contradicts · an ❓ OPEN item the log says is closed · a number corrected elsewhere and stale here.
3. **COMPACT** — identify what in the section is **not one of the named slots** (the three rungs plus
   the three decision buckets). **That is overflow by definition.** Route it: a settled decision → story
   log + ✅ LOCKED · a dead end → story log + ⛔ RULED-OUT · an open thread → open loops + ❓ OPEN · a
   resource → key resources · pure choreography → drop it.

⛔ **Archive first, fail closed — nothing leaves without a receipt.** Before removing one line:

```bash
python3 "$ROOT/system/tools/save/pad_archive.py" archive "<abs brief>" --heading "<the EXACT section heading, copied verbatim>"
```

**Exit 0 plus a `RECEIPT` is the only licence to remove anything.** Non-zero → **stop, remove nothing,
say so.** *(It does not fuzzy-match, by design — read the heading off the brief and pass it verbatim,
or pass explicit line numbers. Finding the section is judgment; matching it is not.)*

⛔ **Propose, never silently apply.** The graduation map goes into the **same** panel as its own
`was → propose → why` item. Show **what moves and where**, not just that something will.
⛔ **Never point the compaction at the rung block.** That is overwritten, never archived, never
graduated — pumping every stale reading into an append-only log makes the record duller each pickup.

**Verify after applying:** re-run `gauge_check.py check` — it must return `ONE-GAUGE`. If it still says
`OVERSIZED`, **say so plainly; do not report the brief clean.** Then stamp:

```bash
python3 "$ROOT/system/tools/save/save_step_ledger.py" stamp graduate "<abs brief>" \
  --heading "<the SAME heading you passed to the archiver>" --ns checkin --verdict DONE
```

**`--heading` is required** — the archive file is named after the exact heading, so the check cannot
know which file proves the section was archived without it. The stamp refuses unless the archive
verifies **and** its newest block postdates this run's start, so a close that skipped the graduation
reports **`✗ MISSED`** rather than reading clean.

**Content deltas may legitimately be empty** — *"current state and success criteria current, no proposed
deltas."* ⚠ **That skip applies only to the content deltas, never to verb B.** In close mode the
graduation runs **whether or not anything is stale.** A section can be entirely accurate and still far
too big — and more importantly, **what this session settled has to leave the section regardless.**
Graduating is not error correction; it is the section's normal metabolism.

## Step 3.57 — The one approval round, and the receipt

**This is the only place this skill asks for confirmation.** Everything before drafts; this shows and
asks, **once.** Front-load approval, spend it at genuine forks, and never dribble small questions across
a run. A skill that stops three times gets skipped entirely.

**One message, every proposal numbered so they can answer `0 yes, 1 no, 2 yes`:**

0. ⭐ **The three rungs — item zero, always first.** `was → propose → why`, per rung that needs one.
   ⛔ Nothing about the block has been written yet and nothing will be until they answer.
   **If no rung needs changing, say so in one line — `rungs: all three current, nothing proposed` — and
   keep the item.** Do not delete it because it is empty: its presence is what says the block was
   examined rather than skipped. Step 0.8 already printed the current text at the top of the reply, so
   they are comparing a proposal against something they have actually read. **That pairing is the whole
   design.**
1. **Plan amendments** — the before→after diff, each carrying its lane, gear tag, named model and
   runnable verify.
2. **Brief deltas** — `was → propose → why`, current state and success criteria.
3. **Routed session findings** — anything mined that lands as a task or a dead end.

**Apply only what they approved.** Never bundle an item they did not see — a batched round is one
prompt, not one blanket yes.

### ⛔ The stop — when a finding needs exploring, hand off

Sometimes acting on a finding requires **verifying something against the real system** — reading files,
running a count, checking whether a thing is actually wired. **This skill does not do that.** It is
expensive, and this runs far more often than planning does.

**So: stop, name what you found, and say to run `/autoplan`.** Do not guess the answer, do not quietly
explore, and do not write a plan amendment resting on an unverified fact.

### 📋 The receipt — mandatory, every run, including when nothing changed

**Emit it always.** It is the one output that makes this observable: without it, a run that looked and
found nothing is indistinguishable from a run that never looked.

State, in one short block:

- **What I compared** — which blocks were read, cold or mid-session · the linked plan · this session.
- ⭐⭐ **The coverage table — paste its stdout. The close is not finished until you have.**
  ```bash
  python3 "$ROOT/system/tools/save/save_step_ledger.py" report --ns checkin
  ```
  ⛔ **This is the only line in the receipt that is not a self-report, which is the entire point.**
  Every other bullet is you describing your own run; this one is a tool describing it. **A close that
  skipped the blind reader cannot render clean** — `reader` shows `✗ MISSED` and the exit is non-zero.
- **What I changed** — each applied edit in one line, or `none`.
- **The altitude block — the TOKENS, not the rungs' text.** ⛔ The receipt is **not** where the rungs
  are printed; step 0.8 already did that, from the file, by code. Printing them twice is how a duty
  drifts. State: `checkin_open`'s verdict **and the line range you passed** (which makes *your* judgment
  auditable too) · `gauge_check`'s verdict · `board_check`'s verdict. Then the audit findings **stated
  independently, never merged** — presence · clarity · drift per rung · plan contradiction — each
  resolving to `current`, `→ proposed as item 0`, or `→ item 0 approved and applied`. **Required even
  when everything else is `none`:** a block that goes unmentioned is indistinguishable from one that was
  never checked.
- **When nothing changed, WHY NOT.** These are not interchangeable and collapsing them is the whole
  failure: *"no stale steps found"* (I compared, it is current) · *"step N looks stale but I wasn't
  confident"* (I found something and deliberately did not act) · *"nothing mined"* versus *"mined, but
  it needs verification — run `/autoplan`."*
  **A bare "plan current — no changes" is a FAILED receipt.**

## Step 3.58 — The handoff proof: a blind reader on the FIXED brief

> **The goal this whole skill exists to serve:** *"a seamless handoff to a blind new session that has
> zero context."*

**Runs AFTER the approved edits are written — never before.** Reading the pre-edit brief answers a
question nobody asked.

> ⛔⛔ **FIRST GATE — two conditions, and either one alone means this does not run.**
> **(a) No edits landed** — there is no fixed brief, so there is no handoff to prove.
> **(b) The `new-session` token was supplied** — this window opened cold and is orienting.
> Either way: **spawn nothing**, and stamp `reader --ns checkin --verdict NOT_OWED`, saying which
> condition applied.
> ⭐ **Why the gate is at the top and not inside.** The reader was reported launching unasked at session
> start **four times**, and every attempted fix landed elsewhere — the cause was one sentence in a
> different file. **The token exists so a cold window is handed the answer rather than deriving it.**
> ⚠ A window that opens with the token and then lands approved edits **owes this step normally.**

**The insight that moved this step.** There were always **two** questions, and one agent was being asked
both:

1. *"What is confusing in the brief right now?"* — **diagnostic.** Wants to run early.
2. *"Can a stranger pick up the FIXED brief?"* — **proof.** Can only run after the edits land.

The goal is (2). (1) measured **redundant** — on one run all four of its findings were roots the foreground
had already found independently. ⇒ **Run it once, after.** Same agent, same cost, better placement.

**The agent: background, cheapest model, read-only, zero session context, TWO files, ONE job.** Spawn
`.claude/agents/worker.md` — read-only by construction, which is the wall.

**What it reads.** *"Read the brief, but SKIP the story log and the scratchpad entirely — do not open
them. Read the linked plan in full."* **Measured on one real brief: the story log was 38.7% and the
scratchpad 38.5% — together 77.2% of the file.** **Why the cut is safe rather than merely cheap:** the
story log is *history* and the scratchpad is *this session's raw notes*; **neither tells a stranger
where the project stands or what to do next.** That job belongs to current state, open loops, the rungs
and the plan — none of which are cut.
⚠ **The risk, stated rather than hidden:** the story log is where *"we tried that and it failed"* lives,
so a reader without it **could re-propose something already ruled out.** Mitigated because the ⛔
RULED-OUT bucket is still read in full. **If a run shows it re-proposing a dead idea, give it that
bucket too — a fraction of the log. Do not hand back the whole thing.**

⭐ **The cheapest model, one job, two files — and being dumber is the CAPABILITY, not a compromise.**
This agent's entire purpose is to behave like a session that knows nothing. A frontier model is the
wrong instrument: it reconstructs intent a stranger would not have, which is the one thing you need it
*not* to do. **Measured:** a mid-tier model on three files and two jobs ran 110,226 tokens in 127
seconds and found nothing; the cheap model on two files and one job ran 53,243 tokens in 68 seconds and
found more.

**The job — quoted rather than paraphrased, because paraphrasing is how the old checklist creeps back:**

> *"This is your handoff. You have zero prior context. Read these files, then tell me: what is this
> project trying to achieve, how would you proceed toward it, what is the single next action you would
> take, and what assumptions are you making to get there? For the next action you name, cite EVERY place
> in the files that names a next action — if two places disagree, say so; that disagreement IS a
> finding."*

⛔ **Why the old question is deleted rather than reworded — both of its shapes were biased instruments.**
A **checklist** ("does the brief point at a done task, is any next action vague…") means the session
decided in advance what could be wrong, so the reader can only find what was already imagined. And
asking *"would you be blocked?"* **makes a model manufacture questions**, which measures nothing.

⭐ **A real run proved it.** One session asked the old question and burned itself on line-count
discrepancies it later admitted were not blockers. A second run, forced to name **the single next
action**, had to go and *find* it — and tripped over a contradiction the first missed. **It was not the
second run that worked. It was the different question.**

⭐⭐ **The assumptions are the measurement.** Every assumption the reader must state in order to proceed
is a gap the brief failed to fill, surfaced unprompted, with nobody deciding the categories in advance.
**That is what replaces the checklist:** not a smarter list of things to check, but a question shaped so
the gaps surface themselves.

**The bar.** Report a gap only if a fresh session would be genuinely **blocked**, **misled into the
wrong work**, or facing a **real contradiction** between two named next actions. Never a stylistic nit,
never "could be more detailed." **Fewer, sharper findings beat a long list.**

**Findings carry section AND line number.** ⛔⛔ **Dedupe on LOCATION, never on SYMPTOM.** A finding is
already fixed only if it points at the **same lines** an approved edit touched. Two findings about one
underlying problem in **two different sections are two findings.** **Worked case:** the reader returned
one finding — the brief still directs to a task that is finished. The foreground had separately flagged
the same staleness in the ground rung. Under dedupe-on-symptom that read as corroboration, so it was
merged into the rung fix and dropped — **but the board still named the finished task, and the board is
what the next session actually reads.** Same symptom, different location; dedupe-on-symptom threw away
the only surviving copy.

**Out-of-scope locations still count.** This agent reads the whole brief, not only the sections this
skill may write. A finding about the decision board, open loops or key resources is reported like any
other — it is not out of bounds just because this skill does not normally touch that section.

### The split — why running late does not mean a second approval round

*"It doesn't ask me permission for facts at all. Judgment you should ask me."* Every finding sorts into
exactly two buckets:

- **FACT — auto-fix, no permission, with a receipt.** Only if it is **mechanically provable from the two
  files**: a bullet naming a task the plan marks done · an `updated_at` older than the newest dated
  content · a pointer to a path that does not exist · a stated count contradicting a count elsewhere in
  the same file. **Fix it, then print one line per fix: what was wrong, what it says now, the evidence.**
- **JUDGMENT — ask, always.** Anything requiring an opinion about what the project means or should do.
  **These come back as ONE final item, never a second full panel.**

⛔ **The seam, stated: the model owns fuzzy judgment; code-provable facts own themselves.** One
permission policy for two kinds of change is the same error as one matcher for two declaration styles.

### ⛔ It runs exactly once. There is no re-verify.

**Fix what it found, report what remains, and stop.** Do not re-run it to confirm a fix.

⛔ **A bounded "run it twice" loop used to live here and was deleted.** *"It should never run or
re-verify ever. That's the point… That is also way over engineered."* **Measured on the run that killed
it:** two passes at 54,493 + 55,861 = **110,354 tokens and about 4.3 minutes** — to confirm a one-line
fact fix, on a reply someone was already waiting for. The second pass returned one fewer finding than
the first, i.e. it re-reported the same open judgment item and confirmed the one thing already known to
be fixed. **It bought nothing.** ⛔ Do not restore it, do not re-add it "just for fact fixes", and do not
make it conditional. **If a fix needs proving, the next check-in proves it** — that is what the next run
is for, and it is free.

### ⛔⛔ Stamp the verdict. This is the step, not a note about the step.

```bash
python3 "$ROOT/system/tools/save/save_step_ledger.py" stamp reader --ns checkin \
  --verdict CAN_PROCEED|BLOCKED|CONTRADICTION|NOT_RUN|NOT_OWED
```

⛔ **`--verdict` is required and the set is closed** — the tool refuses anything off-list, so the
outcome crosses into code as a member of a bounded set rather than as prose. **`NOT_RUN` does not buy a
clean table:** it renders `✗ MISSED`, exactly like no stamp at all. **Admitting you skipped the step is
not the same as doing it.**

⭐ **Why a command and not a sentence.** A full run once happened — rungs printed, both gates passed,
14,868 characters compacted, four panel items approved and written — and **this step was simply
skipped.** Someone asking *"did the reader run?"* is the only reason anyone knew. **The contrast inside
that one run is the whole evidence:** the three tool-backed checks fired every time, because each
returns an exit code; **the one prose-only step fired never.**
⚠ **The honest bound:** the reader writes no artifact, so this stamp is **self-reported**. **It catches
forgetting, which is the measured failure. It does not catch lying, and that is not claimed.** What
changed is the rung — skipping now means omitting a **command** whose absence renders `✗ MISSED`,
instead of omitting a **sentence** nobody could audit. ⛔ Do not "strengthen" this by wording it harder.

## Step 3.6 — Harvest

Two captures, both autonomous, one combined receipt.

**(a) Rot-prone notes → the scratchpad.** Scan the session: *is there any detail — an observation, a
number, a decision in motion, a loose thread, a "watch out for X" — that could rot over a long session
and is worth keeping for this project?* Project-relevant only. **Prune and update; do not append
blindly.** A big chunk becomes a pointer, never a dump.

**(b) Confirmed decisions → the story log and the board. Append-only, journal-first.**
`{date} — tried/decided X → outcome (worked | failed | partial) → STATUS: locked | superseded-by:<entry>
| open → why`. If it overtakes a prior decision, tag the **old** entry `superseded-by` — **the only
in-place change allowed.** Never delete, prune or rewrite. Set the affected decision's bucket; a newly
ruled-out path gets a one-line ⛔ RULED-OUT entry pointing at its story-log entry. **Journal-first:** the
matching journal line goes down before or as you write the brief. **Only what was genuinely confirmed
this session** — an unresolved question is `open`, never `locked`. When unsure, `open`.

> ⛔ **The compaction happened at step 1.8, not here, and never twice in one run.** Do not call the
> archiver here, do not print a compaction receipt here, and **do not "catch up" a compaction you think
> step 1.8 skipped** — if it skipped, it said which gate failed, and that is the honest answer.
> ⭐ **What this harvest writes is for the NEXT compaction, and that is correct.** It lands in the pad
> after the diff on purpose: the pad is ephemeral, so writing to it here does not break the invariant.

**One receipt:** *"📝 scratchpad +N · 📖 story log +M · ⛔ ruled-out +K — [terse list]."* Nothing rose to
the bar → say so in one line. **Never manufacture entries.**

## Step 4 — Offer the deep pass

The harvest captured the ephemeral notes and appended the confirmed decisions. **The heavy curation —
extract, tier, route, the session-close roll-up — belongs to `/save`.** Offer it in one line; do not do
it here.
