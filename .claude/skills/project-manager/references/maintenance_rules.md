# Maintenance Rules

A project doc should be edited continuously, not merely appended.

## When to update

Update the project doc when durable information appears:

- new facts
- new user decisions
- test results
- changed constraints
- changed goals
- expert feedback
- new hypotheses
- disproven/deprecated hypotheses
- current state changes
- future plan changes
- important artifacts
- important user theories
- important boundaries or safety concerns

Do not update for every minor conversational sentence unless it changes future work.

## How to update

When adding new information:
1. Place it where it belongs, not automatically at the bottom.
2. Update the current state if needed.
3. Move completed active items into past/results.
4. Mark deprecated beliefs.
5. Update future plan and next action.
6. Update confidence labels.
7. Keep navigation accurate.

## Periodic maintenance

When the project doc becomes long or messy:
- compress repeated points
- merge overlapping sections
- split overloaded sections
- update the top-level current state
- remove stale next actions
- preserve test results
- preserve why decisions changed
- mark deprecated theories
- keep open uncertainties visible
- improve headings/navigation

## Past / present / future motion

Continuously move information through the work state:

- Future plan becomes present action.
- Present action becomes past result.
- Past result becomes lesson, decision, or deprecated path.
- New evidence revises the current model.
- Revised model changes the future plan.

## Do not lose

Do not delete:
- failed tests that prevent repeated work
- exact values that matter
- user preferences
- safety boundaries
- reasons for decisions
- unresolved conflicts
- important minority hypotheses
- expert feedback

## Over-compression warning

If maintenance makes the project doc too thin to rehydrate from, restore detail.

High information-to-words ratio means dense and complete, not minimal.
